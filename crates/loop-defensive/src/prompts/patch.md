Run the defensive workflow for $1 using only the `mcp__defensive__*` tools. Do not use Loop's own read, write, edit, bash, grep, find or ls tools: they act on this machine, while `mcp__defensive__read`, `mcp__defensive__write`, `mcp__defensive__edit` and `mcp__defensive__bash` act inside the network-less sandbox on a copy of the code.

$1 is a CVE id, a GitHub repository URL, or a local folder. If it is a relative folder path, turn it into an absolute path first (relative to the current working directory). Any language works: for a CVE, the hidden security tests come from the upstream fix (Go, Python, JavaScript/TypeScript, Rust, Java, Ruby and PHP projects).

1. Call `mcp__defensive__prepare_task` with target "$1". Show me the stage reports it prints. If it says the target cannot be worked on, explain why and stop.
2. Identify the bug: call `mcp__defensive__get_task`, then investigate with `mcp__defensive__list_directory`, `mcp__defensive__search_code` and `mcp__defensive__read` until you know the vulnerable code and its root cause.
   - For a CVE, the task describes the known vulnerability; find it in the code.
   - For a GitHub URL or local folder, no vulnerability is known in advance. Assess the code: call `mcp__defensive__run_analyzer` with "all" and confirm or dismiss each lead by reading the code, and map the untrusted-input entry points (HTTP handlers, form and URL input, DOM sinks such as innerHTML, parsers, deserialization, exec, SQL, file paths, auth, crypto, secrets) and where that data flows. Pick the most severe issue that untrusted input can actually reach. Tell me what you found and why you chose it before patching. If you find nothing real, say so and call `mcp__defensive__finish_task` instead of inventing a bug.
3. Reproduce it with a small test that FAILS on the current code, written with `mcp__defensive__write`:
   - Go: a new `*_test.go` file, run with `mcp__defensive__bash` (for example `go test ./<pkg> -run TestRepro -v`).
   - Any other language: a file in the project's test layout (for example `test/repro.test.js`, `tests/test_repro.py`, `spec/repro_spec.rb`, `src/test/java/.../ReproTest.java`, `tests/repro.rs`), run with `mcp__defensive__bash`. `mcp__defensive__get_task` shows the language, build command and test command; use the project's own test framework when it has one, otherwise the language's built-in one (`node --test`, `python -m unittest`, a shell script for C).
   For a repo target this test is the grader's oracle, so it must check the security property itself, not an implementation detail of your fix.
4. Patch it: make a minimal change to non-test source files with `mcp__defensive__edit`. Do not change dependency manifests or lockfiles (go.mod, package.json, requirements.txt, Cargo.toml, ...).
5. Verify: re-run your reproduction test (it must now PASS), then run the project's existing tests (`go test ./<pkg>`, or the test command from `mcp__defensive__get_task`) with `mcp__defensive__bash` to check for regressions. Use `mcp__defensive__show_diff` to review the change.
6. Report: call `mcp__defensive__submit_report` with the summary, root cause, affected files, vulnerable lines as `path:start-end`, the fix, and the exact before/after results of your test and the regression run. For a non-Go repo, also pass `repro_command`: the command that runs ONLY your reproduction test (non-zero exit while vulnerable, zero once fixed).
7. Call `mcp__defensive__grade_patch`. Show me its stage reports. If it is not verified, use its feedback, fix the code in the same workspace and call `mcp__defensive__grade_patch` again.
8. Finish with a short summary: the bug, the root cause, your fix, your verification, and the grader's verdict (and score, for a CVE). For a repo target, remind me that the verdict rests on your own reproduction test and the finding should be reviewed by a human. Tell me where the patch file is (`runs/.../attempt-N/candidate.patch`) so I can apply it to my copy; the original repository or folder was not modified.
