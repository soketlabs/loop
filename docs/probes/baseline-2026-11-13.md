## Load baseline

The tool is `crates/loop-runtime/tests/load_baseline.rs` (ignored test). Its
header lists every parameter. It builds one Runtime over the `faux` provider.
Each model call streams 100 text deltas of 16 bytes. A turn commits about 112
Updates (100 chunks and about 12 more). A counting wrapper around the Event
Log counts `append_batch` calls. Four fast subscribers read the broadcast
channel. The Runtime sends one update per commit, so calls and events are
equal (max batch size is 1). All runs use 2 turns per session.

Config names in the tables:

* `default`: 32 sessions, 16 client tasks, Runtime limits at their defaults
  (16 sessions, 8 active turns).
* `r200`: 200 sessions, 50 clients, limits raised to 200 and 50.
* `r1000`: 1000 sessions, 200 clients, limits raised to 1000 and 200.
* `mismatch_200_defaultlimits`: 200 sessions, 50 clients, default limits.
* `slow_*`: as the named config, plus one subscriber that sleeps 5 ms per update.
* `sqlite` is `SqliteEventLog`. `memory` is `MemoryEventLog`. Both sit under the counter.

Columns: "Commit" is the time of one `append_batch` call. "Delivery" runs from
the return of the commit to the moment a subscriber receives the update.
"End-to-end" runs from the start of the commit call. "Peak turns" is the most
turns started and not ended (from committed `TurnStarted` and `TurnEnded`).
Values are the median of the runs. Ranges are in brackets. Reps is the number
of runs. Peak RSS is the process peak (`getrusage`), and includes about 19 MiB
before the run starts.

### What the load runs show

* The Event Log is the bottleneck, and only the SQLite log. With the memory
  log, 200 sessions and 50 active turns finish in under 2 seconds at about
  25,000 commits per second. With the SQLite log the same load takes 153 to
  170 seconds (dev) or 71 to 77 seconds (release-like) at 270 to 640 commits
  per second.
* The SQLite log gets slower as the log grows. At 8 active turns and 7,000
  events it commits about 2,000 per second (dev). At 50 active turns and 45,000
  events it commits about 280 per second. Commit time per call is 160 ms at
  the median, because all 50 clients wait for the one writer.
* Probable cause: `append` in `crates/loop-runtime/src/log/sqlite.rs` calls
  `latest()` for each Update. That query is
  `SELECT COALESCE(MAX(session_seq),0) FROM events WHERE session_key=?`. The
  index `events_session_seq` is partial (`WHERE session_seq IS NOT NULL`). The
  planner cannot use it for this query, so each call scans the whole table.
  Check with bundled SQLite 3.46.0 on a 51,200-row table: the query plan is
  `SEARCH events` and a call takes 8.7 ms (dev profile). With
  `AND session_seq IS NOT NULL` added, the plan uses the covering index and a
  call takes 0.010 ms. The group commit in the writer does not help, because
  the cost is per event, not per transaction. This was not changed. It is an
  input for the refactor.
* At 1000 sessions and 200 clients, the SQLite log did not finish in the
  400 second deadline: 577 of 2000 turns (dev) and 837 of 2000 turns
  (release-like). No turn failed and no open was refused. Peak concurrent
  turns was 110 and 111, below the 200 asked, because clients wait for commits.
  Peak RSS was 881 MiB (dev) and 763 MiB (release-like).
* With the memory log, 1000 sessions and 200 clients finish in about 9 seconds
  (dev). The peak RSS is about 2.8 GiB, or about 2.8 MiB per session. At 200
  sessions it is about 590 MiB (2.9 MiB per session). This includes the events
  that the memory log keeps. No limit on the active turns bounds it.
* Default limits with 200 sessions (`mismatch`): `new_session` was refused with
  `Busy` 183 times (dev) and 180 times (release-like). Only 17 and 20 sessions
  opened and finished their turns. The Runtime had its 16 sessions loaded when
  the refusals began. This is the failure mode when clients outnumber the
  limits. I did not trace why no idle session was unloaded to make room here.
* Lag: with fast subscribers, no receiver lagged in any run, even at 200
  sessions. The broadcast channel holds 4096 updates, shared by all sessions.
  One slow subscriber (5 ms per update) lagged in all 4 runs that had one.
  It skipped 2,516 updates (default, sqlite, dev) and 40,368 updates (r200,
  memory, dev). The delay is pooled over the 5 subscribers, so it mixes the slow
  one with 4 fast ones. Pooled p95 was 2.4 seconds (default, sqlite, dev). Pooled
  p99 was 0.4 seconds (r200, memory, dev). The Runtime kept running and every
  turn completed. The Runtime's per-Session pump reads the Session's own
  channel, not this one.
* Peak concurrent turns matched the limit at the default config (8) and at
  r200 with the SQLite log (50). With the memory log, turns end so fast that
  the peak stays at 3 to 6.

### Noise

seconds, r1000 memory: 7.7 to 19.6 seconds). The SQLite runs vary by less than
10 percent. Compare the SQLite numbers and the shape of the curves. Do not
compare single memory-log wall times.

## Store suites

Both suites live in the crate `crates/core/loop-store-testkit`. A store outside
this repository adds the crate as a dev-dependency and calls a suite function
with a factory. The factory returns a fresh, empty store in a `Fixture` (which
can also keep a temp dir or a database alive).

Event Log suite (`loop_store_testkit::event_log`): `run_all`, `round_trip`,
`concurrent_producers`, `cursors`, `generations`, `atomic_validation`,
`invalid_unknown_is_atomic`, `runtime_records_have_no_session_cursor`,
`subagent_sessions`, `prompts_sent`. Each has a `*_on` form that takes a log you
already hold. `crates/loop-runtime/tests/event_log.rs` runs it on the memory
and SQLite logs. All 23 tests there pass. The SQLite-only tests stay in that file.

Session store suite (`loop_store_testkit::session_store`): `run_all`,
`create_and_load`, `list`, `append_entry_order`, `concurrent_appends`,
`read_entries_after_seq`, `read_path`, `leaf_moves`, `fork`, `delete`,
`open_writer`, `trait_defaults`. Each takes a factory and a `Capabilities`
value. `crates/core/loop-store-testkit/tests/session_conformance.rs` runs it
on the memory, SQLite and JSONL stores (36 tests). The three older test files
in `crates/loop-agent/tests` are unchanged.

### Differences between the Session stores

The suite does not skip a check where stores differ. A `Capabilities` field
declares the behavior, and the suite asserts it. If a store changes, its check
fails. `Capabilities::strict()` is the behavior a new store should aim for.

| # | Difference | memory | SQLite | JSONL |
|---|---|---|---|---|
| 1 | DEFECT. Concurrent appends to one Session keep the chain (`concurrent_appends_form_one_chain`) | yes | yes | NO |
| 2 | `read_entries(Some(n))` skips the first n entries | no, ignored | no, ignored | no, ignored |
| 3 | Order of `list` | none (hash map) | oldest first | newest first |
| 4 | `delete` of a missing id | succeeds | succeeds | `NotFound` |
| 5 | `parent_session_id` of a fork | source id | source id | source file path |
| 6 | A fork keeps entry ids | yes | no, new ids | yes |
| 7 | `metadata().path` | none | none | set |
| 8 | `read_path_to_root_or_compaction(Some(unknown))` | empty path | `NotFound` | empty path |
| 9 | `create_surface_destination` on a plain store | `Invalid` (trait default) | `Invalid` (needs a leased writer) | `Invalid` (trait default) |
| 10 | `write_cancellation()` on a plain store | none | none (a leased store returns a token) | none |

Notes:

1. This is a bug, not a design choice. Evidence: 8 tasks append 8 entries each
   to one JSONL Session. All 64 entries are stored, but 4 of them have no
   parent (4 roots) and the parents are spread over 21 to 33 distinct ids.
   Five runs gave the same 4 roots. Cause: `KeyedOperationQueue::enqueue`
   removes the key's tail when an operation starts and puts a new tail back
   only when it ends. An operation that arrives meanwhile finds no tail and
   runs at once. The unit test in that file passes only because its operations
   do not await. Memory and SQLite keep one chain. The suite declares the
   JSONL value so the suite passes, and still checks that every entry is kept.
2. All three readers ignore `after_seq`. The sequence number is not visible
   through the trait, so `n` means "skip the first n entries in append order".
   The suite checks that a store declaring the filter does it.
3. Only the order of `list` differs. The suite checks that ordering when a
   store declares it.
4. Deleting twice behaves like deleting a missing id in each store.
5. JSONL stores the path of the source file in `parent_session_id`. Other
   code that reads this field as an id will not match for JSONL forks.
6. The SQLite fork replays the copied entries as new writes.

Other checked behavior that is the same in all three stores: metadata round
trip, `NotFound` for a missing Session on load, append and fork, every
`PendingSessionWrite` kind becomes an entry that chains to the leaf, leaf
moves (`Leaf` entries), compaction paths (with and without a kept range),
all four fork selections, errors for a missing or unknown fork target (no
Session is left behind), `open_writer` equal to `load` on these stores, and
`release_leases` succeeding.

## Findings

* SQLite Event Log commit cost grows with the log size (see "What the load
  runs show"). This limits the Runtime to a few hundred commits per second
  after tens of thousands of events.
* JSONL Session store loses the entry chain under concurrent appends
  (difference 1).
* Shared target dir: Cargo hashes path dependencies of a workspace by their
  path inside the workspace, so two git worktrees that share
  `CARGO_TARGET_DIR` share their artifacts. After another worktree changed
  `loop-protocol`, a build here failed with
  `missing field tool_lock in initializer of RuntimeStatus` in
  `crates/loop-runtime/src/runtime.rs`, although this tree has no `tool_lock`.
  A private target dir fixed it. Agents that share a target dir can hit the
  same error or, worse, link the wrong artifact without an error.

## Not measured

* Shipping-profile (LTO) numbers. The release-like profile has LTO off.
* Subscriber delivery delay from the moment the agent emits an update. The
  envelope has no timestamp, so the delay starts at the Event Log commit.
* E1 and E7 on the shipping build, and E7 at its full 1000 schedules (200 run).
* A remote or networked Event Log or Session store. Only the stores in this
  repository ran the suites.
* Per-session memory with the SQLite log at 1000 sessions: the run did not
  finish, so the peak RSS is for the first 577 (dev) or 837 (release-like) turns.
