## Settings bug: `project_overlay` resets keys that a project file omits

- **Confirmed on `staging`:** yes. I confirmed it by reading the code. The
  file `crates/loop-app-core/src/config/settings.rs` is byte-identical on
  `staging` and `main`. No test covers it. (The author of #106 reports a
  throwaway test on `main` that showed the bug.)
- **Where:**
  - `settings.rs:501` `merge_project` calls `project_overlay` (line 510).
  - Unconditional assignments in `project_overlay`:
    line 516 `default_thinking_level`, 517 `theme`, 518 `compaction`,
    539 `enable_skill_commands`, 540 `quiet_startup`, 541 `hide_thinking_block`,
    542 `double_escape_action`, 543 `ui_mode`, and 636
    `response_header_timeout_ms`.
  - A partial workaround exists only for line 636, in `load_settings`
    (lines 652 to 656): it reads the raw JSON and copies the global value
    back if the project file has no `responseHeaderTimeoutMs`.
- **Description:** `Settings::load_file` fills every key that a file omits
  with its serde default. `project_overlay` then copies these fields from the
  project value to the global value without asking whether the project file
  set them. So a trusted project whose `.loop/settings.json` only sets, for
  example, `mcpServers` silently resets the user's global `theme` to `dark`,
  `defaultThinkingLevel` to `off`, `uiMode` to `normal`, `quietStartup` and
  `hideThinkingBlock` to `false`, `doubleEscapeAction` to `tree`,
  `enableSkillCommands` to `true`, and `compaction` to its defaults. This
  also contradicts `docs/configuration.md` ("Project values override global
  values"). The workaround covers only one key, and it is applied only in
